# 可视化数据与空间逻辑

这份参考把“画得好看”进一步拆成可检查的视觉数据模型。它适用于车云架构、数据采集链路、平台融合、角色流程、指标测算和对标页面。页面不是把文字放进框里，而是把业务事实转换成可读的对象、关系和坐标。

## 先把事实转成视觉数据

在画图前建立一张最小视觉数据表。每个图形对象至少具备以下字段：

| 字段 | 说明 | 例子 |
| --- | --- | --- |
| 实体 | 页面上要被识别的对象 | APP端、车端、车云大数据平台、售后团队 |
| 实体类型 | 决定它可以与什么对象比较 | 数据源、平台、能力层、角色、指标 |
| 属性 | 对象的可比较特征 | 定位、数据域、技术栈、部署形态、状态 |
| 数值与单位 | 可以被大小、位置或表格编码的量 | 费用/年、人数、车辆数、准确率、时间 |
| 时间与范围 | 数值或结论适用的周期和边界 | 2026年、国内、海外、某车型、短期方案 |
| 状态 | 事实所处阶段 | 已有、部分已有、待建设、建议、预计、待确认 |
| 关系 | 对象之间的业务关系 | 采集、传输、存储、依赖、共用、隔离、对标 |
| 来源 | 能回溯到的材料、页码或计算 | 文件名＋第3页、数据表＋口径 |

如果一个对象只有名字，没有关系、属性或来源，它通常不应独占一个图形。可以把它放进列表、表格或附注，避免“有框就有含义”。

## 视觉编码字典

同一页中固定一个编码只表达一个维度。下表是默认语义，用户模板或材料图例优先。

| 视觉变量 | 默认编码 | 适用场景 | 使用限制 |
| --- | --- | --- | --- |
| X位置 | 顺序、时间、横向比较、区域 | 流程步骤、国内/海外、平台列 | 没有共同横轴时不要让左右位置暗示高低 |
| Y位置 | 能力层级、流程阶段、角色层、优先级 | SaaS/PaaS/IaaS、采存管服、上下游 | 同一页要先定义“越上越高”还是“越上越晚” |
| 宽度 | 覆盖范围、时间跨度、可用空间 | 区域覆盖、阶段区间、横跨多个平台的共享能力 | 只有范围可比较时使用，不能用宽度暗示重要性 |
| 高度/面积 | 数量、容量或强度 | 成本柱、人数柱、流量或规模图 | 必须有数值轴、比例或图例；架构框的大小默认只表示容器，不表示能力强弱 |
| 颜色 | 类别、主体、状态或重点 | 平台归属、问题风险、整合核心 | 一种颜色只承担一种含义；颜色本身必须有文字或图例 |
| 填充深浅 | 次级/重点、状态强弱 | 背景分组、主次层级 | 没有量化尺度时不能当连续数值使用 |
| 边线样式 | 边界、隔离、规划范围 | 安全隔离区、方案范围、待确认边界 | 虚线不默认代表未建设，必须在本页说明 |
| 线宽 | 流量、强度或重要关系 | 数据流量、投入比重、关键路径 | 无量化口径时用统一线宽，避免伪造权重 |
| 箭头 | 方向、调用、因果、推进 | 数据流、审批、业务闭环 | 邻接关系不必画箭头，避免把布局顺序误读成因果 |
| 容器 | 归属、边界、管理范围 | 平台、区域、能力层、组织 | 容器嵌套要有真实层级，避免把每个短语都做成卡片 |
| 留白 | 分组、阶段、优先级间隔 | 业务区域与技术区域分隔 | 留白不能替代分组标签 |

禁止把多个变量叠在同一视觉元素上。例如用红色、加粗、放大、右移同时表达“高风险、重要、数量大、未来方案”，读者无法知道哪一层含义是真的。拆成多个明确编码或回到表格。

## 页面坐标就是数据结构

写图之前先定义坐标轴和固定槽位：

```text
页面 = 页首判断区 + 主体坐标区 + 口径/来源区
主体坐标区 = 行语义 + 列语义 + 对象槽位 + 关系层 + 图例
```

每个槽位要能回答“为什么在这里”。常用坐标结构如下：

| 坐标结构 | 行 | 列 | 适合表达 |
| --- | --- | --- | --- |
| 能力矩阵 | 能力层级 | 平台/品牌/区域 | 重复、共用、独有、缺口 |
| 数据链路 | 处理阶段 | 数据源/数据域 | 来源、内容、系统、落点 |
| 流程图 | 业务动作或阶段 | 角色/责任方 | 谁在何时做什么 |
| 对标表 | 比较维度 | 当前/目标/对标对象 | 同口径差距 |
| 方案测算 | 指标 | 基线/方案/差额 | 收益、代价、假设 |
| 角色价值图 | 用户角色 | 任务、能力、结果 | 业务价值如何产生 |

一旦行和列确定，同类对象必须占据同一对齐线。不能为了填满空间把一个平台放在左边、另一个同类平台放在右上，再通过颜色让读者猜它们可比较。

## 参考材料中的空间语法

### 车云隐私数据采集存储管理 V1.0 第3页

这页适合定义为四列数据结构：`采集触点 → 采集数据内容 → 数据传输系统 → 数据存储地`，APP、车端、店端作为行对象。视觉上，列标题是字段，行是来源，横向排列让每个来源的路径可以逐行追踪。

复用时先生成一张关系表，再把每一行投影到四列。不要先画四个大框，再把所有系统名堆进最后一列。若某个来源没有明确的内容、系统或落点，标记“材料未说明”，不要用相邻行的值补齐。

### 车云隐私数据采集存储管理 V1.0 第4页

这页是过程坐标：横向或顺序编号表达动作先后，控制说明贴在对应动作附近。七个步骤分别是数据清单确认、采集与授权开发、隐私政策更新、用户授权、采集、存储、使用。步骤名称是动词，步骤下的说明是该步骤的约束或产物。

复用时每个步骤只放一个主要动作；如果一个步骤同时有开发、授权、日志和删除，就拆成主动作与旁注，不能让一张流程图承担多条时间线。流程箭头只表示先后或处理方向，不能由箭头宽度暗示数量，除非已经有流量口径。

### 智能车云与 SDA 融合建议第5、15页

平台为列、SaaS/PaaS/IaaS或应用/平台/资源为行。相同高度表示同一能力层，跨列横条表示共用能力，列内模块表示平台独有能力。国内与海外的并列关系使用独立边界表达，不能把它们画成同一部署实例。

### 阿维塔 VHR 对标第4–6页

第4页按车云查询、智能诊断、能耗管理、事件推送分行，把平台数量和平台名称放在同一阅读路径中，底部再放权限隔离与统一入口，表示“分散平台造成障碍，产品中枢承接障碍”。第5页用左侧纵向系统链路定位缺失服务层，右侧表格对齐相同对比维度。第6页左侧三层架构与右侧三段职责同高，形成图文锚定。

这种布局中，左图不是装饰，右表也不是重复说明：左图回答缺口在哪里，右表回答差距体现在哪些业务维度。若两边都写完整长句，页面会失去主次。

### 车云、阿维塔、深蓝数据平台融合分析第8、11页

第8页把业务应用、统一服务、统一湖仓、统一接入、IaaS分层，并把治理贯穿与AI挂接作为横向能力放在层级之外。这里的横向框不是一个普通流水线步骤，而是作用于多个层的治理或供数关系。

第11页以“采、存、管、服”构造纵向业务结构：底部是数据源和标准，中间是清洗、湖仓、资产与质量，上部是数据APP、智驾数据闭环、停车补能和监管服务。它同时表达数据处理顺序和服务对象，因此不要把所有模块改成同一层的横向卡片。

## 从数据到页面的工作顺序

1. 抽取事实：对象、属性、指标、时间、范围、状态、来源。
2. 归类实体：哪些是来源、平台、能力、角色、指标或决策项。
3. 画关系矩阵：记录采集、流向、包含、共用、依赖、隔离、对标等关系。
4. 选择坐标：确定行、列、顺序轴、边界和主阅读方向。
5. 分配视觉编码：先编码最重要的关系，再处理类别、状态和数量。
6. 加入口径：给数字、颜色、虚线、线宽和方案状态提供图例或脚注。
7. 投影成图：保持同类对象对齐，让图与表、标题、结论共享术语。
8. 反向校验：从图上任取一个对象，能否还原它的实体、关系、数值口径和来源。

## 数据图和架构图的区别

- 数据图中大小、位置、线宽可以表达数量、规模、时序或流量，但必须有刻度或图例。
- 架构图中大小通常表达容器范围，位置表达层级和归属；框越大不代表能力越强，颜色越深不代表数据量越大。
- 流程图中箭头表达先后或依赖；没有时间或状态数据时，不要画成趋势图。
- 对标图中同一行必须是同一比较口径；想表达多个指标时拆行或改成小表，不用一个“综合大小”替代。

## 可视化交付检查

- 每个对象是否有实体类型、状态、关系和来源？
- 位置是否表达了明确的行/列/顺序语义？
- 颜色、大小、线型、箭头是否各自只表达一个维度？
- 数量是否有单位、基线、分母、时间和图例？
- “已有、待建设、建议、预计、待确认”是否被区分？
- 图和表是否分工，是否避免同一句话重复两遍？
- 去掉颜色后，关系是否仍能通过标签、位置和线条读懂？
- 页面缩小后是否仍然知道主链路和主结论？
