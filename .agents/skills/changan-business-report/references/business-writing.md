# 业务叙事与精炼措辞

## 把技术情况变成业务判断

参考材料有三种不同重心：

- SDA融合：业务定位、架构现状、重复投入与体验影响、行业对标、融合可行性、方案取舍、待决策事项。可行性分架构、技术栈、功能与APP说明，并保留时间、人力和用户影响。
- VHR对标：为谁服务、提供什么能力、现状在哪里阻塞、差距是什么、短期场景与长期平台如何推进。将研发术语转换成售后可执行的信息。
- 数据平台融合：各平台定位与重叠、整合层次、共用底座和品牌业务的边界、成本与效率、需求与使用场景。目录中有草稿与重复页，不照抄其全部页序。

根据任务选择叙事主线，不要求每份汇报都包含以上全部章节。

## 页首短句怎么写

一条句子承担一个判断，通常用“短标签：具体事实/判断＋直接影响”。先具体对象，再动作与结果。

| 用途 | 写法骨架 | 应保留的信息 |
| --- | --- | --- |
| 定位 | 由谁牵头，为谁提供什么能力 | 牵头方、服务对象、业务边界 |
| 现状 | 哪些对象处于什么状态 | 时间、范围、已有能力 |
| 问题 | 什么障碍，导致谁多做了什么 | 机制与业务影响，不只写“效率低” |
| 差距 | 双方在同一维度的具体差异 | 基准、分母、口径差异 |
| 方案 | 统一哪层，保留哪层，通过什么实现 | 变更边界、职责、依赖 |
| 收益 | 按什么基线，预计改善什么 | 单位、周期、假设、测算状态 |
| 计划 | 谁在何时完成什么 | 牵头、配合、交付物，缺失则待确认 |

参考原句的价值在于具体，例如VHR第4页“一线团队需要跨专业找人、跨平台找数据”，直接说出了成本发生在哪里。不要压成“存在协同痛点”。

## 总览页和流程页的顺序

车云隐私数据采集存储管理V1.0第3–4页提供了一个很好的业务技术材料写法：先总览，再展开。

- 总览页回答“对象从哪里来、经过什么、落到哪里”。把入口、数据内容、传输/处理系统、存储地放在同一条主链路上；多个入口用同一套列结构对齐，读者可以直接比较它们经过的环节。
- 流程页回答“事情怎样发生”。把流程拆成连续的业务动作，使用编号和动词，例如确认、开发、更新、授权、采集、存储、使用。每个步骤保留一个动作和最必要的控制说明，避免在步骤标题中塞入背景段落。
- 两页之间保持同一组对象和术语。总览页出现的来源、系统和落点，应能在流程页找到对应动作；流程页新增的控制点要放在发生它的步骤旁边。
- 页首标题直接命名正在说明的对象，正文先给一句主判断，再用图承担细节。不要把总览和流程压在一页，也不要用长段落代替图的顺序关系。

这套写法适合数据采集、系统接入、平台融合、审批和服务闭环等材料。只有在流程确实存在、来源和去向明确时才使用；没有证据的步骤保留为待确认，不为补齐箭头自行添加环节。

## 从工程语言到使用动作

VHR第5页把“DTC / Log / 波形”与“现象 / 风险 / 话术 / 指引”放在同一对标维度。它表达的是数据如何成为业务可使用的产品，不是简单把技术名词换成通俗词。

写能力时补全以下关系，选择本页需要的部分：

`数据/信号 → 分析能力 → 可交付信息 → 使用者动作 → 业务结果`

箭头在这里代表处理或使用顺序。不能仅因为排成链条，就声称结果已经实现。

例如以下为**写法演示，不是公司已实现事实**：

- 空泛：“依托数据底座全面赋能售后提质增效。”
- 具体：“汇聚单车故障记录，向售后提供预检报告，减少跨平台查询。”
- 若仅有方案依据：“拟汇聚单车故障记录，为售后预检提供统一入口。”

同样，“统一平台”至少说明接入、治理、计算、服务或业务应用究竟统一哪一层。来源只说统一接入，就不能扩写为统一存储与全部业务。

## 精炼时删什么、留什么

删掉无事实支撑的“全面、深度、持续赋能、打造领先、显著提升”等修饰；用具体能力、动作和条件补足含义。来源中的战略原话确需引用时保持引用身份。

删掉与图重复的长段组件枚举。图已有接入、湖仓、服务节点，页首应说明整合边界或业务作用，而非再次列一遍技术栈。

保留会改变结论的词：预计、约、目标、建议、部分、本阶段、某车型、国内/海外、某类场景。不要把“预计节省”改为“节省”，不要把“综合准确率”与“大事故准确率”混作同一指标。

短标签采用平行语法，但不强凑三个词、三个价值或三个阶段。允许4个角色、2个方案、5个平台，数量由内容决定。

## 对标、测算与计划

- 对标表每行只比较同一个维度：服务对象、数据表达、协同链路、场景覆盖、部署、技术栈等。不要左侧写问题、右侧写不可验证口号。
- 原稿数字只能作为历史材料引用。VHR第5页“综合准确率约80%”与“大事故准确率95%”的分母不同，不得据此得出整体提升15个百分点。
- 融合分析第5页的收益拆为资源、人力、效率三类，可以学习拆分方法；不要把其金额、数量和收益比例写成后续项目默认承诺。缺单位与测算疑点应核对，不能静默补齐。
- 方案对比同时交代收益与代价。SDA第16–19页的时间、人力、用户影响是一种有用的可行性表达维度，不代表后续项目可沿用相同估计。
- 短期写具体服务场景和可验收结果；长期写能力结构与边界。没有来源的负责人、日期、投资额保持待确认，不为排版完整自行编造。

## 压缩示例

以下均为基于来源意思的改写示范，非逐字引用：

| 来源 | 可学习的表达 |
| --- | --- |
| VHR第2页 | 定位：研发牵头、面向售后的车辆全生命周期运维监控平台 |
| VHR第4页 | 现状：专业平台分散，一线跨专业找人、跨平台找数据 |
| VHR第5页 | 差距：缺少把研发数据转成售后处置指引的服务中枢 |
| SDA第15页 | 融合边界：统一底层平台能力，保留品牌个性化业务 |
| 融合分析第8页 | 整合重点：共享湖仓与服务能力，业务应用保留各自职责 |

是否使用以上句子仍取决于本次材料是否支持，不把历史案例当现状。
