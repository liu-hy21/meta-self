# 关系深度工作台设计

| 项 | 内容 |
|---|---|
| 日期 | 2026-11-10 |
| 状态 | 待确认 |
| 选择方案 | 多页面深度工作台 |
| 首个人物 | bc |

## 1. 意图

把当前 `/relation/profile` 的“关系分类 + 日志表单”升级成一个可持续使用的关系研究工作台：先管理人物，再进入某个人物的聊天原文、数据分析和 AI 分析。第一位人物为 `bc`，使用已经整理好的本地聊天档案作为原文来源。

成功标准：用户能在 10 秒内找到 bc，能按日期和关键词阅读原文，能看到有解释的关系指标，并能一键生成带证据范围的 AI 分析；AI 结论必须和原文区分，不能伪装成事实或心理诊断。

## 2. 目标

- 重构关系入口为人物管理页，展示人物状态、标签、最近互动与聊天档案状态。
- 提供独立的原文查看页：按日分组、时间范围筛选、关键词搜索、发送者筛选、消息类型标记。
- 提供独立的数据分析页：消息量、双方占比、活跃天数、活跃时段、回复间隔、连续对话、周/月趋势、话题关键词。
- 提供独立的 AI 分析页：关系温度走势、双方沟通画像、聊天主题、关系转折点、值得留意的信号和可执行的下一步。
- 让每个 AI 结论能回到对应日期或消息区间；生成失败时显示原因，不编造结果。
- 复用现有 Prisma 用户、`RelationPerson`、`RelationPersonKind`、`RelationInteraction` 及现有左侧导航，不破坏其他域。

## 3. 非目标与反目标

- 第一版不做多平台聊天自动同步，不接入微信账号或远程爬取。
- 第一版不把 11,114 条聊天消息全部写入 Prisma；原文档案保留在本地服务端文件，按需解析，避免把个人聊天复制进浏览器 bundle。
- 不把“性格分析”呈现为人格诊断、医学结论或确定性标签；所有表述都使用“从聊天中观察到的倾向 / 证据不足”。
- 不给关系打总分或做道德排名；关系温度是可解释的观察指标，不是对人的评价。
- 不在没有明确配置模型密钥时假装完成 Codex 分析；无模型时可显示本地统计和“尚未生成 AI 分析”。

## 4. 方案对比

### 方案 A：单页关系工作台

把人物、原文、分析和 AI 全部放在 `/relation/profile`，使用页内 Tab 切换。

优点：切换快、实现量小。缺点：原文阅读和分析的状态容易互相干扰，URL 无法表达当前视图，也不适合未来多人物深度比较。

### 方案 B：多页面深度工作台（已选择）

人物管理、人物详情、原文、数据分析、AI 分析分别拥有清晰 URL，并通过人物上下文导航互相跳转。

优点：信息架构清晰、可深链接和保留筛选状态，适合后续加入更多人物与更多档案来源。缺点：需要建立统一的人物上下文导航和更多查询层。

### 方案 C：独立聊天中心

聊天记录成为一级模块，关系页只负责人物和摘要。

优点：适合未来管理多类聊天数据。缺点：关系和聊天被拆散，当前需求中的“围绕人物理解关系”会变得不连贯。

选择方案 B，因为用户明确要“多页面深度工作台”，同时当前数据模型已经有关系人物和互动实体，可以以较小的 schema 扩展完成长期结构。

## 5. 页面与路由

### 5.1 人物管理 `/relation/profile`

- 顶部：关系工作台标题、人物数量、最近同步时间、添加人物按钮。
- 主体：人物列表卡片；bc 作为首个卡片，显示标签“朋友”、消息数、最近消息、档案时间范围和“已导入”状态。
- 侧栏或底部：现有手工互动记录入口，保留 `RelationInteraction` 的快速记录能力。
- 空状态：没有聊天档案的人物仍可创建，只显示互动记录和“等待导入”。

### 5.2 人物详情 `/relation/people/[personId]`

- 作为人物上下文主页，展示关系摘要、最近互动、原文/数据/AI 三个入口。
- 显示标签、备注、数据来源、档案覆盖区间和最近一次分析时间。
- 支持修改人物名称、标签和备注；不允许从 UI 删除原始聊天档案。

### 5.3 原文查看 `/relation/chat/[personId]`

- 顶部固定人物上下文栏，包含返回人物、时间范围、搜索框、发送者和消息类型筛选。
- 左侧日期锚点或月份索引；中间按日分组的原文时间线；右侧显示当前筛选结果和档案状态。
- 文本消息显示原文；图片、语音、视频、表情、位置、应用消息显示类型占位符和时间；不把解析摘要替换成原文。
- 支持“只看我 / 只看对方 / 全部”，支持 2026-07 至 2026-10 的预设范围。
- 首版采用服务端分页/分段读取，避免将完整聊天文本一次性发给客户端。

### 5.4 数据分析 `/relation/analysis/[personId]`

首版指标：

- 总消息数、双方消息数与占比、活跃天数、最长连续对话天数。
- 按日/周/月的消息量趋势。
- 24 小时活跃热力图与工作日/周末差异。
- 回复间隔的平均值、中位数、P90；区分双方，缺少连续消息边界时标记估算。
- 会话段数量、平均会话长度、最长会话长度。
- 文本/图片/语音/视频/表情等消息类型分布。
- 话题关键词排行，展示词频与代表性日期，不把词频直接当成关系意义。

图表优先使用轻量 SVG/CSS，不新增大型图表依赖。

### 5.5 AI 分析 `/relation/analysis/[personId]/ai`

- 关系温度走势：按周生成 1–5 的观察分，展示趋势、证据数量和不确定性说明。
- 双方沟通画像：表达节奏、回应方式、主动性和情绪表达方式；只写“倾向”，不写人格诊断。
- 聊天主题罗列：主题名称、出现频次、代表性日期、最近变化。
- 关系转折点：消息密度、语气、主题或回复节奏明显变化的区间。
- 关系中的正向信号 / 需要留意的信号 / 可尝试的一步。
- 每张 AI 卡片显示生成时间、使用的数据范围和“查看证据”链接。
- 生成按钮明确说明会把所选聊天内容发送给配置的 Codex/OpenAI 兼容模型；没有配置时保持禁用并提示配置项。

## 6. 数据与服务端设计

### 6.1 人物与档案映射

扩展 `RelationPerson`，增加可选的聊天来源字段：`sourceType`、`sourceKey`、`archivePath`、`archiveStart`、`archiveEnd`、`messageCount`、`importedAt`。bc 的 `sourceType` 为 `WECHAT`，`sourceKey` 为 `wxid_en8z2t73paw522`。

新增 `RelationAiReport` 保存人物、时间范围、模型、状态、内容 Markdown、证据范围和生成时间；避免每次刷新都重新调用模型。

聊天消息不落 Prisma。`src/lib/relation/chat-archive.ts` 只允许读取配置的本地档案目录，负责解析 Markdown/JSONL、按范围和关键词筛选，并返回服务端 DTO。个人聊天原文目录加入 `.gitignore`，不得进入客户端静态资源。

### 6.2 查询层

新增 `src/lib/relation/`：

- `people.ts`：人物列表、人物详情、标签和最近互动。
- `chat-archive.ts`：档案发现、解析、分页、搜索和消息类型归一化。
- `metrics.ts`：消息统计、时间统计、会话切分、词频与趋势计算。
- `ai-analysis.ts`：构造 Codex 输入、脱敏/截断策略、调用与落库。
- `types.ts`：页面 DTO、图表点位、证据引用类型。

所有服务端查询都从 `getAppUser()` 获得用户，不接受客户端传入的 userId。

### 6.3 AI 边界

- 默认只发送用户主动选择的人物和时间范围；不发送其他人物、其他域数据或数据库凭据。
- Prompt 要求输出结构化 JSON/Markdown，包含结论、置信度、证据日期范围和不确定性。
- 分析前先完成本地统计，模型只解释已计算的数据与抽样原文，不负责重新计算总量。
- 调用失败、超时或未配置密钥时，保留本地统计，显示可读错误状态。

## 7. 视觉方向

当前应用是像素化暖纸色监视器风格；关系工作台将保留 MetaSelf 的“个人操作系统”语义，但关系深度页采用更克制的“档案研究台”子风格：深墨绿主背景、暖纸色内容面、珊瑚色温度强调、细线网格、窄字宽数字与明确层级。避免把聊天分析做成通用 SaaS 卡片墙。

- 人物管理偏档案柜：列表、标签、最后活动和档案状态。
- 原文查看偏编辑室：日期刻度、纸张内容面、清晰的长文本阅读宽度。
- 数据分析偏仪表盘：小面积图表、醒目指标、趋势和异常注释。
- AI 分析偏研究笔记：证据标记、信号卡片和渐进式展开，避免大段无依据的“心理画像”。

## 8. 约束与风险

- 11,114 条 bc 聊天记录会显著增加原文页的读取量，需要分页或按日分块。
- 当前导出包含媒体占位符而非媒体文件，第一版只保证原文消息行完整，不承诺媒体预览。
- 当前项目的 LLM 配置是 OpenAI 兼容 `LLM_API_KEY / LLM_BASE_URL / LLM_MODEL`；“通过 Codex”需要沿用该服务端配置，不在浏览器中暴露密钥。
- Prisma schema 当前存在关系人物模型，但 `createRelationPerson` 只支持最小创建；需要补充校验、重定向和首人物种子/幂等初始化。
- 现有左侧导航保留 `/relation/profile` 入口，新增页面通过人物上下文导航进入，避免影响其他域。

## 8.1 构建口径（审阅后已确定）

- 当前产品按单用户本机应用处理；bc 档案路径通过环境变量或项目约定目录配置，默认读取 `bc_chat_2026-07_to-2026-10.md`，不依赖浏览器上传。
- 档案格式为 UTF-8 Markdown；消息行包含时间、发送者和正文/类型占位符。解析器保留原始行序号，生成稳定的本地消息引用 ID，便于证据跳转。
- 当前账号为“我”，`bc` 为对方；展示和计算统一使用 `Asia/Shanghai`，日期范围为闭区间。
- “会话段”定义为相邻两条消息间隔不超过 45 分钟；连续同方消息保留为独立消息，但回复间隔只统计跨发送者的相邻消息。
- 活跃天数按当天至少有一条非空消息计入；系统消息计入原文数量，但不计入双方占比和回复间隔；媒体占位符计入消息量。
- 关系温度趋势先由本地确定性基线计算：活跃度、互惠度、跨日持续性、回复节奏和正向表达等特征归一化到 1–5；AI 只负责解释变化、补充主题和不确定性，不直接凭空生成分数。
- 证据首版定位到稳定消息引用和日期区间，不要求像素级高亮；点击证据可回到原文页并带上 `message` 查询参数。
- 同一人物、范围和模型重复生成时保留历史版本，默认展示最新一版；失败记录保留错误状态，可重试。
- bc 的人物初始化放在关系入口的服务端幂等 ensure 流程中：按用户 + `sourceType=WECHAT` + `sourceKey` 查重，已有同源人物不重复创建。

## 9. 验收标准

- 打开关系入口能看到 bc，重复刷新不会生成重复人物。
- 从 bc 详情可进入原文、数据分析和 AI 分析三条路径，并且 URL 可直接打开。
- 原文页能在 2026-07 至 2026-10 范围内显示 11,114 条消息的分段结果，筛选后条数和原文日期一致。
- 数据分析的总数、双方数量、月份数量与本地导出数据一致；空数据人物有明确空状态。
- AI 分析没有模型配置时不会报 500；有配置时结果落库并显示生成时间与证据范围。
- 所有敏感聊天内容只在服务端按需读取，不被静态打包；原始微信目录与解密中间产物不被修改。
- `npm run lint` 与 `npm run build` 通过。

## 10. 实施顺序

1. 加入人物/档案字段与 bc 幂等初始化；补充服务端档案读取类型。
2. 完成人物管理和人物详情页，接入现有关系互动数据。
3. 完成原文查看页及分页、筛选、日期锚点。
4. 完成本地数据分析与 SVG/CSS 图表。
5. 完成 Codex AI 分析调用、证据引用和结果落库。
6. 全局导航、响应式、可访问性、构建和视觉验收。
