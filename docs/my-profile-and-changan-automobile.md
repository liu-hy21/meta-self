### 车型层级与架构路由

deepdata 把车辆数据的常用层级定义为：

`品牌 → 车系 → 车型配置 → VIN`

其中车系通常使用 `car_series_code / car_series_name`，车型配置使用 `car_conf_code / car_conf_name`，VIN 用于单车粒度分析。资料中明确提醒，口语中的“车型”有时实际指车系，有时指车型配置，查询前需要先确认粒度。

品牌维度通常通过 `car_brand_name / brand_name` 与车系维度关联。deepdata 的产品车型搭载映射中存在不少“搭载品牌”和“搭载车系”为空的记录，这类记录只能说明功能或指标已经进入产品清单，不能直接证明某个品牌或车系已经搭载；真正做品牌对比时，应回到车辆维表、车型配置表或功能搭载明细表补齐映射。

SDA 车系的示例编码包括 `C390`、`C390S`、`C798`、`CD701`、`CD701REEV` 等，完整清单应以实际维度表为准。SDA 与非 SDA 车系不能简单共用一套来源表：SDA 通常走 `dw.dws_vhc_idv_sda_*` 表族，非 SDA 走 `dw.dws_vhc_idv_*` 表族；混合车系查询需要按架构分别取数后再 `UNION ALL`。

### 指标和数据治理习惯

deepdata 中反复出现的基础指标包括：联网车辆数、实名认证车辆数、上电车辆数、搭载车辆数、使用车辆数、使用次数、使用时长、使用率、活跃率、留存率、推送/安装/升级成功率，以及车辆诊断、维保、安全守护、电池管家和用车报告等服务指标。

在使用这些数据时，资料要求特别注意以下口径：

- 默认过滤测试车：`is_ca_car = '1'`，并排除配置编码中带 `-T` 或 `TEST` 的车辆。
- 需要实名车辆口径时，使用实名认证状态和实名认证通过时间进行过滤。
- 分区表必须带 `p_day` 或 `p_month`；`_ds` 通常代表日快照表。
- 使用 incall 行为表按车辆聚合时，关联键优先使用 `car_id`，不能直接假设 `vin` 一定可用。
- “智驾里程”定义为 ACC + IACC + NOA 使用里程之和，不能与总里程或 CLTC 标称续航混用。
- 同一功能可能存在 CIIA、SDA、EPA 深蓝、TIV 或 MQTT 等不同来源，指标定义和埋点不能跨架构直接拼接。

### 与我的岗位的关联

从公开公司战略与 deepdata 数据体系的交集看，我的工作处在以下几个方向的交汇处：

1. **车云数据链路**：车辆、车机、手机 App、云端服务之间的数据采集、传输、加工与服务化。
2. **指标与语义层**：把“联网、上电、搭载、使用、活跃、留存、成功”等业务概念沉淀为可复用指标。
3. **多架构数据统一**：处理 SDA、CIIA、EPA 深蓝及非 SDA 数据来源的路由、字段差异和合并口径。
4. **车型与功能分析**：围绕品牌、车系、车型配置、VIN 和功能搭载关系，支持车型对比、功能渗透和用户使用分析。
5. **数据质量与治理**：关注测试车排除、实名认证、分区、埋点、车系映射、数据延迟和指标一致性。

结合品牌矩阵后，可以进一步把我的工作上下文理解为“多品牌、多架构、多产品域的数据统一”：

- 对长安、启源、深蓝、阿维塔和凯程，需要先统一品牌、车系、车型配置和 VIN 的主数据关系，再谈功能使用或用户活跃对比。
- 对同一项能力，例如远程控车、车辆诊断、用车报告、OTA、地图、语音或智能驾驶，需要区分“是否搭载”“是否上电”“是否使用”和“使用效果”，不能只看一个埋点次数。
- 对新能源品牌，能源、电池、充电、续航和能量管理会成为重要的数据主题；对凯程，还需要考虑商用车运营和车队服务；对阿维塔，则会更多涉及高端智能电动和智能座舱体验。这些是分析重点的差异，不代表每个品牌都只使用某一类数据。
- 跨品牌比较时，首先应确认架构路由和指标口径，再比较渗透率、使用率、活跃率、留存率、升级成功率或服务质量。

### 可以沉淀为个人工作方法的品牌分析框架

以后遇到“某品牌/某车系表现如何”的问题，可以按下面的顺序拆解：

1. **主体确认**：品牌、车系、车型配置、VIN 的范围是什么。
2. **架构确认**：SDA、CIIA、EPA 深蓝、TIV 或 MQTT 的数据来源是什么。
3. **资产确认**：相关功能是否有搭载映射、指标卡、事实表和维度表。
4. **生命周期确认**：搭载、联网、实名、上电、首次使用、持续使用和流失分别如何定义。
5. **指标确认**：比较车辆数、次数、时长、成功率、活跃率或留存率中的哪一种。
6. **结果解释**：把品牌定位、产品类型和数据结果放在一起解释，避免用单一功能使用量代表品牌整体表现。

### 车云数据安全：采集流向与控制点

来源：[海外欧洲数据采集参考方案（2025.04.08）](<company材料/车云数据安全-贺总汇报/【参考材料】海外(欧洲)数据采集方案-车云平台-v1.6.3.pptx>)、[车云隐私数据采集存储管理（2026.11）](<company材料/车云数据安全-贺总汇报/车云隐私数据采集存储管理V1.0.pptx>)、[数据安全管理平台实施方案（2026.01）](<company材料/车云数据安全-贺总汇报/数据安全管理平台实施方案.PPT>)、[语音数据信息安全汇报（2026.08）](<company材料/车云数据安全-贺总汇报/语音数据信息安全汇报20260814.pptx>)、[车联网数据中台隐私数据合规排查大纲（2026.11）](<company材料/车云数据安全-贺总汇报/车联网数据中台隐私数据合规排查大纲.html>)。

- **三端到站点的横向流向**（隐私管理第 3 页、欧洲方案第 2 页）：从左到右依次是采集触点、采集数据、传输系统、存储地。左侧 APP 端对应账号和埋点，车端对应 CAN 信号与座舱埋点，店端对应人车卡基础数据；中间经过车云 TSP、数据湖仓，右侧到各站点数据中心。箭头和“加密传输、脱敏/加密处理”标注位于环节之间，表示控制点落在流转链路，而不是只在最终数据库。
- **采集流程的两种方向**（隐私管理第 4 页、欧洲方案第 3 页）：图上方横向排列采集清单确认、数采及授权/取消功能开发、隐私协议更新；下方又列数据存储、数据采集、用户授权、数据使用，并在对应模块旁标“作用”和“安全策略”。前者是建设工作流，后者是数据生命周期与用户控制，不能把页面的横向排列误当作数据实际传输顺序。
- **账户数据的泳道**（隐私管理第 7–9、11 页、欧洲方案第 4 页）：从左到右为用户/APP 触点、TSP 服务、数据库；从上到下为购车、注册、控车、分享，底部另开注销和删除路径。HTTPS 标在触点到 TSP 之间，AES 标在 TSP 到数据库之间；删除请求从 APP/TSP 指向数据表。图中的“删除请求待建设”“当前逻辑删除、后期物理删除”是该版本标注的状态，不能写成已完成能力。2026 管理稿这几页基本重复同一张图。
- **数据使用的贯穿控制**（HTML 排查大纲）：按采集、传输、存储、使用四环节检查，覆盖采集清单、告知同意、敏感信息、传输加密、数据分类分级、权限审计、保存期限、出境路径及个人权利响应。它是逐项排查框架和整改清单，不是已经通过检查的证明；具体法规与期限应在正式使用前由合规团队核对。
- **语音业务的双路径图**（语音汇报第 2 页）：左侧“场景一”是车端音频和 VIN 到云端语义识别、语义理解，复杂意图再到 ANCLAW，结果返回车端；右侧“场景二”是音频到云端存储和模型训练。两路并列说明实时推理与训练复用涉及不同的数据目的。第 3–7 页分别讨论现有防护、TARA、DPIA、语音处理/删除风险和大模型安全计划；“语音删除暂无整改方案”是材料在 2026.08 的状态陈述。

### 数据安全管理平台的部署视角

[数据安全管理平台实施方案](<company材料/车云数据安全-贺总汇报/数据安全管理平台实施方案.PPT>)虽然扩展名为 `.PPT`，实际是可读取的新版演示文稿，已检查其第 2–6 页及第 3 页架构图。

- **业务架构图的左右关系**（第 3 页）：左侧为车联网 CAN、埋点、数采等业务来源；中间为数据基座和数据安全管理（数据集成、开发、调度、质量、审计、权限、分类分级）；右侧并列“数据分类分级”和“隐私合规管理”。后两块是治理与合规能力，不是前面数据基座的普通业务应用。顶部同时标有业务应用和运维运营人员，表明平台服务不同角色。
- **业务架构图的上下关系**（同页）：下层为 GDC、水土机房中的实时/离线计算与 ODS、DW、DM 数据层，数据向上进入基础管理、分类分级、隐私合规模块。图中的多个向上箭头代表底层资产为上层治理能力供数；左右并列的两处 MySQL/Redis 与文件存储分别支持不同模块，不能据图推断为一个统一数据库。
- **部署方案**（第 4 页）：材料提出数据安全和隐私合规模块采用高可用双活；业务应用位于 GDC 和水土机房虚拟机，数据及中间件使用水土私有云服务。第 5–6 页另列 Prometheus 监控、告警与事件处置通道。这些属于 2026.01 的实施方案和决策材料，应在系统现状核验后再标记为“已部署”。
